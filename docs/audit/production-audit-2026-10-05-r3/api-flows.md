## Shared request/response rules

- Public discovery/file/terms/contact endpoints permit a guest. Supplying a JWT invokes the normal validation path; a public route is not a reason to expose private entity fields.
- Protected requests validate access-token purpose/expiry/revocation/session cutoff, current account activity and authorities. Admin non-auth requests require enrolled MFA when production policy is enabled. URL roles and method capabilities compose with service ownership checks.
- IDs never confer entitlement by themselves. Owner helpers resolve the current principal to a stored user/provider and compare ownership; booking/chat/safety helpers resolve customer/provider participation or explicit admin capability.
- Bean Validation runs for annotated DTOs; request maps, query fields, multipart headers and free text rely on explicit length/enum/range/pagination/file checks. The inventory reproduces DTO constraints and reachable business error keys. ORM constraints are an additional backstop, not a friendly input validation policy.
- Success generally wraps a DTO/list/page in `ApiResponse.Success`; creates explicitly use201 where coded. The exact return signature is retained per endpoint. Exceptions pass through GlobalExceptionHandler; filter errors use the matching structured shape. Context-dependent errors include400 invalid input/state,401 session/purpose credential,403 role/owner,404 missing/hidden resource,409 uniqueness/version,429 budget,413 file size and503 unavailable dependency. Confirmed unexpected500 paths are B-06/07. Validation of a foreign ID may deliberately use404 to avoid enumeration.
- The inventory's reachable operation list follows statically resolvable service/helper calls, including conditional paths and overloaded methods. It does not claim all operations execute for every request, nor that it resolves every ORM callback/lazy getter/framework authentication operation. Database repositories/queries and entity relations were separately reviewed; performance/lock behavior still needs PostgreSQL runtime measurements.

This matrix describes current implementation, not a proposed policy specification. `Perms` comments retain a broad-read default; B-04 identifies the resulting sensitive exposure and inconsistent capability scope, rather than claiming the server violates its own ANY_ADMIN annotation. Product/security owners must decide the least-privilege read policy and encode it across routes, DTOs, inbox and tests.

## Consumer and unused-endpoint assessment

No endpoint is declared unused purely because a current frontend lacks a call. Reflection/framework mappings, public-site fetches, scheduled jobs, scripts/runbooks, tests and external operator entry points were considered. Provider/account/customer mutations are chiefly mobile; admin moderation/user/finance/audit/settings are chiefly dashboard; discovery/auth/terms/contact overlap. Current dashboard consumer routes are individually mapped in [dashboard.md](dashboard.md). The legacy settlement helper/endpoint remains a compatibility/operator candidate; the local dev reset is profile-selected. There is no repository evidence sufficient to delete either. Broad inventory methods with no discovered client consumer should be documented and checked against live access/owner records before deprecation.
